# Alembic Migration Plan

## Goal

Add database migrations so Dynasty HQ can evolve SQLite schemas safely without relying only on `SQLModel.metadata.create_all()`.

Current state:

- Models are defined in `app/models/__init__.py`.
- Database startup is handled in `app/db.py`.
- `init_db()` currently creates missing tables with `SQLModel.metadata.create_all(engine)`.
- There is no migration history, schema versioning, or upgrade command.

Target state:

- Alembic owns schema changes.
- Existing local databases can be upgraded without data loss.
- New installs still bootstrap cleanly.
- CI can detect model/schema drift.

## Principles

- Keep SQLite as the primary supported database.
- Make the first migration a baseline that matches the current model schema.
- Do not introduce destructive schema changes in the Alembic adoption PR.
- Keep startup behavior friendly for local-only users.
- Document manual backup steps before running migrations.

## Phase 1: Add Alembic Dependency and Config

Tasks:

- Add `alembic` to the Python dependencies in `pyproject.toml`.
- Run `alembic init migrations`.
- Configure `alembic.ini` and `migrations/env.py` to use the app database URL.
- Import `SQLModel.metadata` and app models in `env.py`.
- Point `target_metadata` at `SQLModel.metadata`.
- Ensure `DYNASTY_DB_PATH` is respected for local, Docker, and test usage.

Implementation notes:

- Use `sqlite:///{DYNASTY_DB_PATH}` for the migration URL.
- Keep migration files in a top-level `migrations/` directory.
- Prefer deterministic generated migration output; review autogenerated revisions manually.

Validation:

- `uv run alembic current` works against a fresh database.
- `uv run alembic upgrade head` works against an empty database.
- Existing tests still pass.

## Phase 2: Create Baseline Migration

Tasks:

- Generate an initial revision from the current SQLModel metadata.
- Review the generated tables, columns, nullable flags, indexes, and foreign keys.
- Add any missing indexes or constraints intentionally.
- Run the migration on a fresh SQLite database.
- Compare the resulting schema against the current `create_all()` schema.

Important review targets:

- `dynasty`
- `season`
- `game`
- `player`
- `playerseasonstat`
- `recruit`
- `setting`

Risk notes:

- Alembic autogenerate may not perfectly represent SQLModel/Pydantic aliases.
- SQLite has limited ALTER TABLE support; future migrations may need batch mode.
- Existing databases created before Alembic need to be stamped or migrated carefully.

Validation:

- Fresh database: `alembic upgrade head`, then full test suite.
- Existing test database: stamp or upgrade path verified with a copied database.
- Confirm app starts and can create/list dynasties.

## Phase 3: Integrate Migrations Into App Startup

Decision to make:

- Option A: Keep app startup simple and require explicit migration command.
- Option B: Auto-run `alembic upgrade head` during startup.

Recommended default:

- For Docker and production-like deployments, run migrations before starting Uvicorn.
- For local development, document `uv run alembic upgrade head`.
- Avoid implicit destructive behavior at startup.

Tasks:

- Update `app/db.py` so `init_db()` no longer hides missing migrations.
- Consider keeping `create_all()` only for test utilities or first-run fallback during transition.
- Add a helper script or documented command:

```bash
DYNASTY_DB_PATH="$PWD/data/dynasty.db" uv run alembic upgrade head
```

Docker option:

- Add an entrypoint script that runs migrations before `uvicorn`.
- Ensure migration failure stops the container.

Validation:

- Docker build succeeds.
- Docker run with empty `/data` creates schema via migrations.
- Docker run with existing `/data/dynasty.db` upgrades schema.

## Phase 4: Add Drift Checks

Tasks:

- Add a CI/local check using `alembic check` once Alembic is configured.
- Add docs explaining when to generate a revision.
- Add a test or command to verify current models do not differ from migration head.

Suggested commands:

```bash
uv run alembic check
uv run pytest
```

Validation:

- A model change without a migration fails the drift check.
- A migration-aligned model change passes.

## Phase 5: Documentation

Tasks:

- Update `README.md` quick-start instructions.
- Add backup guidance before migrations:

```bash
cp data/dynasty.db data/dynasty.db.backup
```

- Document local migration workflow.
- Document Docker migration behavior.
- Document recovery if migration fails.

## Rollout Plan

1. Add Alembic configuration and baseline migration.
2. Test on a fresh database.
3. Test on a copy of an existing database.
4. Update Docker startup or docs.
5. Add drift checks.
6. Merge only after full test suite and manual app smoke test pass.

## Acceptance Criteria

- `uv run alembic upgrade head` creates the current schema on an empty SQLite database.
- Existing copied database can be brought under Alembic control without data loss.
- `uv run pytest` passes.
- Docker deployment still starts with a persistent `/data` volume.
- README includes migration and backup instructions.
- Future schema changes have a clear migration workflow.
